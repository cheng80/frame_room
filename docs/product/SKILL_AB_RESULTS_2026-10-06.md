| 색/알파 기준 | 실제 PNG. GIF/WebP 미리보기 인코더 차이를 화질 점수에 넣지 않음 |
| 자동 처리 | 각 제품 경로의 자동 선택을 그대로 기록. 시작 구간/앵커/보정 기본값이 달라 순수 버전 효과로 해석하지 않음 |
| 같은 구간 | 기존 `[41,69)`, 새 `[17,41)` 고정. RIFE 끄고 현재 RGBA와 최신 fixed를 비교 |
| RIFE 통제 시험 | 동일한 기존 영상의 28장 PNG 해시, 동일 RIFE 실행 파일·v4.6 모델, 32장 출력, 위상 회전 없음, 동일 1,167ms 표시 |

프레임룸은 실제 `process_clip → normalize_frames → finish_frames → render_occurrence → write_animation_formats`를 호출했다. 작업자 전체는 DB 쓰기가 있으므로 실행하지 않고 최소 snapshot/파일 resolver로 같은 렌더 설정을 전달했다. API/UI 작업 접수·프로젝트 ZIP·승인 gate를 실행한 E2E 시험은 아니다. 각 폴더의 `ui-differences.json`에 범위를 기록했다.

최신은 설치된 스킬의 정식 `video-frames`, `video-loop`, `video-cycle-align`을 호출했다. 공용 스킬과 프로젝트 엔진 소스를 바꾸지 않았다. 두 버전의 모든 기본값을 억지로 같게 만들지 않고, 자동 처리와 통제 시험을 분리했다.

주의: 현재 기본 GIF 모드와 RGBA 모드는 **팔레트뿐 아니라 축소 방식도 다르다.** 또한 최신 `--anchor none --cycle fixed`에는 기존부터 있던 작은 점 제거가 작동한다. 기존/새 영상에서 각각 448/495 source 픽셀을 제거했으며, 정규화 결과의 다른 픽셀 합계는 880/840이다. 따라서 같은 구간 비교를 ‘새 리샘플러만의 개선’으로 해석하지 않는다. 현재 영상 RGBA 축소 함수 자체는 최신과 동일하다.

## 자동 처리 결과

| 입력 | 현재 앱 선택 | 최신 motion-auto 선택 | 현재 보정 켬 | 최신 보정 켬 |
| --- | --- | --- | --- | --- |
| 기존 | start 41, 28장, 1,167ms | start 26, 28장, 약 1,167ms | 원본 61번 1장 교체 | 선택 주기 내부 8·24·16번, 3장 교체 |
| 새 | start 17, 24장, 1,000ms | start 17, 24장, 1,000ms | 원본 21·37번, 2장 교체 | 선택 주기 내부 4·20번, 2장 교체 |

원본 인덱스는 0부터 시작하고 end는 exclusive다. 표의 ‘원본’과 ‘선택 주기 내부’ 번호를 구별한다. 보정 개수가 많다고 품질이 높다는 뜻은 아니다. 최신의 motion-auto는 몸 위치 정합도 적용하므로 같은 구간이라도 현재 앱과 전체 좌표가 같지는 않다.

최신의 크기 유지 보정은 두 입력에서 모두 적용되지 않았다. 측정 drift는 기존 0.0001, 새 0.0008로 1% 조건 미만이다. 이번 영상으로 `size_hold`의 실효성을 입증하지 못했다.

시각 검수에서 현재 기본 GIF 결과는 이진 알파와 팔레트 마무리로 윤곽이 더 단단하게 보이고, 현재 RGBA와 최신 고정 구간은 반투명 가장자리가 남는다. 이것은 출력 성격 차이다. 후속 부위별 비교에서도 최신이 장갑의 기준색을 복원하지 못했고, 원본 영상의 변색이 남아 있음을 확인했다.

## 후속 검수: 흐릿함과 팔·장갑의 누런색

사용자는 최신 결과가 더 흐릿하며 팔의 누런색이 다시 보인다고 지적했다. 새 생성 없이 같은 저장 프레임을 분석했다. 확대 이미지는 실험 폴더의 `softness-8x.png`, `arm-color-stages.png`다. 측정 기록은 [알파 비교](comparisons/sprite-gen-v2.34.0/blur-check.json), [팔·장갑 색 비교](comparisons/sprite-gen-v2.34.0/arm-color-check.json)이며 재현 도구는 `scripts/skill_compare/inspect_softness.py`, `inspect_color.py`다.

**흐릿함:** RIFE를 끈 같은 구간의 축소 후·앵커 배치 전 결과를 비교했다. 프레임당 평균 반투명 픽셀은 현재 기본 0개, 현재 RGBA는 기존/새 585.4/557.1개, 최신 RGBA는 583.9/554.9개다. 현재 RGBA와 최신 fixed의 전경 RGBA 일치는 각각 98.72%/98.25%이며 기존 작은 점 제거 차이가 포함된다. 반투명 개수는 지각 선명도 점수가 아니지만, 현재 기본과 최신의 차이에 GIF 마무리·축소 방식이 크게 작용함을 보여준다. 새 블러 필터나 RIFE 탓으로 단정하지 않는다. **현재의 또렷한 기본 GIF 마무리를 유지하고, 보간 불량 거절은 별도로 이식한다.**

**변색:** 기준 그림의 갈색 장갑과 달리 기존·새 Grok 원본 영상에 노랑/올리브색이 이미 생겼다. 인물 기준 좌우와 혼동하지 않도록 아래는 화면 오른쪽의 빈손 쪽 장갑, 화면 왼쪽의 크림색 소매로 구분한다. 원본 인덱스는 0부터 시작한다.

| 검사 부위 | 원본 프레임·좌표 | 원본 RGB → 배경 제거 RGB | 확인 범위 |
| --- | --- | --- | --- |
| 기존 빈손 쪽 장갑 | 41, `(360,295)` | `(193,173,87)` → 동일 | 지정 ROI의 노랑/올리브 RGB 범위 209개 모두 불변 |
| 새 빈손 쪽 장갑 | 17, `(374,278)` | `(94,82,15)` → 동일 | 지정 ROI의 같은 RGB 범위 68개 모두 불변 |
| 새 화면 왼쪽 소매 | 25, `(249,229)` | `(189,175,124)` → 동일 | 소매 내부 ROI 682개 전체 RGB 불변. 기준 그림부터 크림색 소매 |

RGB 범위 집계는 수동 지정 ROI 내 진단이며 자동 재질 분류나 전체 프레임의 색 안정성 점수가 아니다. 장갑 ROI 전체에서는 기존 16/683개, 새 13/509개 불투명 픽셀의 RGB가 배경 제거에서 달라졌다. 따라서 모든 픽셀이 원본과 같다는 뜻도 아니다. 양쪽 버전의 keyed 결과는 앞서 확인한 대로 동일하다.

단계 확대 이미지에서 기존 영상은 현재 GIF 마무리로 장갑의 노랑이 갈색에 가까워지지만 최신 RGBA에는 남는다. 새 영상은 현재 기본에도 올리브색이 남는다. 과거 수정은 누락된 참조·축소·GIF 마무리를 복구한 것이며, 영상 모델이 바꾼 재질색을 모든 입력에서 복원하는 기능은 아니었다. 따라서 **최신 이식만으로 색 문제 해결 또는 최종 화질 승인으로 처리하지 않는다.** 후속 P1-06에서 기준색 비교·선택 영역 보정·시간축 검수를 다룬다. 이번에는 제품/사용자 결과의 자동 재색칠을 하지 않았다.

## 동일 입력 RIFE 통제 시험

기존 영상 고정 구간의 동일 28장으로 실제 RIFE를 실행했다. 네 장은 원본 시각과 일치하고 나머지 28개 출력 슬롯은 두 원본 사이 시각이다.

| 항목 | 현재 엔진 | 최신 v2.34.0 |
| --- | ---: | ---: |
| 출력 프레임 | 32 | 32 |
| 중간 결과 채택 | 28 | 20 |
| 불량 거절 후 가까운 원본 선택 | 0 | 8 |
| 같은 최신 진단기로 출력 재측정 시 경고 슬롯 | 10 / 28 | 0 / 28 |
| 최대 dark excess | 0.884% | 0.086% |

근거: `shared-rife/*/resample.json`, `shared-rife/quality.json`. 최신의 `bleed`와 `between=auto` 조합이 검은 오염을 제한하는 실제 차이를 보였다. 다만 같은 판정기로 다시 잰 수치라 독립적인 사람의 품질 평가가 아니며, 가까운 원본으로 대체하면 움직임이 잠깐 멈춰 보일 수 있다. ‘불량 거절’과 ‘모든 중간 자세 복원’을 구별한다.

추가로 최신 정식 `video-cycle-align --length 32 --view side@right` 실행:

- 기존 자동 결과: 보간 21장 채택, 7장 원본 대체, 시작 발 `right`, 재촬영 안내 없음.
- 새 자동 결과: 보간 18장 채택, 6장 원본 대체, 시작 발 미확정. 원본이 그림을 두 프레임씩 유지해 12 drawings/s로 측정됨. 32장·1,333ms로 늘리면 9 drawings/s가 되어 `held-drawings` 안내 발생.
- 이는 위의 동일 입력 통제 시험과 다른 실행이다. 선택 구간·위상·최종 시간이 달라 수치를 섞지 않는다. 재촬영 안내가 있어도 이번 승인 범위인 영상 1회를 넘겨 재생성하지 않았다.

## WebP 실패 원인: 설치 문제가 아님

프레임룸 기본 GIF 마무리에서는 PNG·GIF·WebP가 성공했다. 기존/새 영상의 RGBA·RGBA+RIFE 네 사례에서는 PNG·strip·GIF가 저장된 뒤 WebP의 전체 RGBA 일치 검증이 실패했다.

| 실제 canonical PNG와 Pillow WebP 비교 | 결과 |
| --- | --- |
| 보이는 RGB 차이 | 네 사례 모두 0 |
| 알파 차이 | 네 사례 모두 0 |
| 프레임 수·시간 | 네 사례 모두 일치 |
| 완전 투명 픽셀의 RGB 차이 합계 | 기존 RGBA 28,852 / 기존 repaired 29,858 / 새 RGBA 39,695 / 새 repaired 39,802 |
| 동일 PNG·시간을 `img2webp -lossless -exact`로 저장 | **네 사례 모두 전체 RGBA·시간 엄격 검증 통과** |

설치된 Pillow 12.3의 `WebPImagePlugin._save_all()`은 애니메이션 인코더에 `exact`를 전달하지 않지만, 단일 이미지 `_save()`는 전달한다. 프레임룸 `_webp()`는 `exact=True`를 넘겼다는 전제로 숨은 RGB까지 검사하므로 이 입력에서 실패한다. 최신 엔진은 `img2webp -exact` 경로를 쓴다. 같은 libwebp 버전이어도 호출 경로가 다르다.

투명 픽셀의 RGB는 현재 화면에서 보이지 않지만 후속 필터링·합성의 엄격 재현 계약에서는 별도로 관리할 수 있다. 검사를 삭제해 통과시키지 않고, 인코더가 계약을 보존하게 하는 수정이 우선이다. 별도 실험용 exact WebP 4개를 만들었으며 **제품 코드는 아직 수정하지 않았다.** 실제 worker는 final-preview 예외로 후보 등록 완료까지 진행하지 못할 수 있어 P0로 기록한다. 이 문제는 PNG 기반 영상 품질 우열과 분리한다.

2. **P0: 보간 출처와 버전별 recipe.** `made_at/nearest_at`을 실제 원본 index·시간·부모에 반영하고 기존 채택 GIF/편집 상태를 보존.
3. **P1: RIFE bleed·불량 거절·held-drawings 진단.** 실제 효과가 확인된 우선 이식 대상. 보간 거절로 늘어난 hold를 사용자에게 표시.
4. **P1: 발 위상/미확정 후보, 주기 의심 검사, 크기 보정.** 앞 둘은 이번 최신 진단에서 동작 확인. 크기 보정·복수 주기·다방향 성능은 추가 회귀 필요.
5. **P1: 장비 좌우·체형 명세, stream 선택 통일.** 코드상 누락을 보완할 후보지만 이번 생성에서는 효과를 비교하지 않음.
6. **P1: 부위별 기준색 유지와 시간축 색상 검수.** 원본 영상부터 장갑의 노랑/올리브 변색이 있고 최신에도 남는다. P1-06을 추가한다. 현재 기본 GIF 마무리를 보존하되 범용 재질색 복원으로 간주하지 않는다. 자연스러운 크림색 소매·피부·금속과 변색 장갑을 구별하며 자동 임의 재색칠은 하지 않는다.

새 RGBA 결과의 원본 프레임 28·39·40은 오른쪽 안전영역(edge=2)을 1px 초과했다. 실제 64×128 캔버스 밖 잘림은 없으며 QA를 숨기거나 수동 승인하지 않았다. 기본 GIF 모드는 이 오류가 없었다.

## 검증과 보존

- 사용자 프로젝트·앱 SQLite 등 **1,182개 파일 해시 불변**. 생성 원본/기존 채택 GIF를 덮어쓰지 않음.
- 새 이미지 결과 1장·영상 POST 1회 확인. 나머지는 로컬 처리. 서버 재시작·프로젝트 등록·승인·커밋·push 없음.
- 프레임룸 canonical PNG/strip parity와 계보·원본 해시 확인. WebP 실패는 실패로 기록, 진단용 exact 인코더 결과와 구분.
- ego-browser의 비교 전용 공간에서 HTML 로드, 두 입력 전환, 재생/정지, 프레임 이동, 원본 MP4 로드, 같은 구간/RIFE 선택을 확인. 개발 서버 없이 단일 파일로 동작.
- 두 버전 전체 테스트·제품 E2E·프롬프트 A/B·통계적 다회 생성 평가·다방향 발 접촉 검증은 미실행. 문서의 ‘통과’는 기록된 기술 검증 범위이며 사용자의 최종 픽셀/동작 승인과 다르다.
