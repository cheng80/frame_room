# 캐릭터 스프라이트 에디터 PRD

버전 1.0 · 2026-10-03 KST · 구현 기준 확정 · 앱 구현/제품 수용 시험 전

## 1. 만들 제품

개인 게임 개발자가 캐릭터 기준 이미지를 등록하고 동작별 스프라이트를 생성하거나 가져와, 체형·발 위치·애니메이션을 편집하고 게임용 파일로 내보내는 로컬 웹앱이다. `sprite-gen`의 Python 엔진을 프로젝트 내부에 포크하고 React UI로 제작 과정을 연결한다.

사용자는 터미널 명령어, run 폴더, 중간 JSON을 다루지 않는다. 첫 실행 이후 프로젝트 생성부터 생성·편집·출력·다시 열기까지 웹 UI에서 수행한다. 개발용 설치 명령과 일반 사용자의 제작 절차를 구분한다.

주 사용자는 혼자 또는 소규모로 2D 게임을 만드는 개발자다. AI 이미지 후보를 바로 게임에 쓰기 어려운 원인은 그림 생성뿐 아니라 포즈별 크기 변화, 무기 잘림, 알파 잔여물, 발 위치 흔들림, 반복 순서와 시간, 저장 결과 불일치에 있다. 이 제품은 그 편집·검수·출력 과정을 연결한다. 모든 생성 결과의 외형 일관성을 자동 보장하지 않는다.

## 2. 근거와 성공 기준

[사용자 합의](../planning/USER_DECISIONS.md), [완료된 조사](../../research/hero-inc/2026-10-03-implementation-design/README.md), [실제 이미지 실험](../../research/hero-inc/2026-10-03-implementation-design/validation.md)을 기준으로 한다. 원작 내부 에디터의 완전한 복제가 아니라 공개 규칙과 기존 엔진을 결합한 독립 제품이다.

성공은 다음 두 여정을 따로 검증하는 것으로 정의한다.

1. **가져오기 여정:** 새 프로젝트 → 기존 PNG/시트 등록 → 알파·영역 검수 → 공통 배율·앵커 → 동작 편집 → 저장·재열기 → 확정 미리보기 → 출력 → 독립 뷰어 재생.
2. **생성 여정:** 기준 이미지와 스타일 참조 → 기준 승인 → provider·동작·프롬프트 설정 → 실제 생성 → 배경 제거·추출 → 위 편집·출력 과정. 단일 프레임 재생성도 새 후보 비교 후 채택한다.

두 여정에서 수동 CLI/JSON 편집 단계는 0개여야 한다. 모의 provider나 기존 PNG 여정만 통과하면 실제 생성 연동은 미검증이다. 모든 필수 요구의 테스트 결과를 남기고, 검증하지 못한 항목 때문에 전체 완료 표현을 완화해야 하면 구체적으로 명시한다.

## 3. 필수 요구

간단한 픽셀 보정은 펜/지우개·색 선택·되돌리기 수준으로 시작한다. 레이어 중심의 범용 페인팅 앱은 목표가 아니다. 복잡한 배경의 완전 자동 제거는 보장하지 않고 지원 한계와 수동 알파 보정/다시 생성 경로를 제공한다.

## 4. 첫 화면과 기본값

프로젝트 목록에서 새 캐릭터 또는 기존 프로젝트를 연다. 편집기는 `기준 자료 → 동작·생성 → 추출 → 정렬 → 동작 편집 → 검수·출력`으로 이동한다. 기존 이미지 사용자는 생성 단계를 건너뛸 수 있다. 어디서든 현재 캐릭터·저장 상태·진행 작업을 확인할 수 있다.

거너 예시는 **선택형 프리셋**으로 제공한다: 512×512 셀, 가장자리 2px, 바닥 여백 18px, 목표 앵커 (256,494), 알파 임계값16·하단12%·최소4px. 8개 키포즈와 6개 동작은 고정 제품 제한이 아니다. 공개 이미지가 제품 기본 에셋으로 재배포 가능한 것으로 가정하지 않는다.

이미 정렬된 입력은 source scale 1 보존 모드로 시작할 수 있다. 목표 체고 조정은 기준 몸 landmark를 승인한 뒤 수행한다. 하나의 프레임만 bbox 높이에 맞춰 확대하는 기본 동작은 없다. 좌우 반전으로 비대칭 장비를 자동 고치지 않는다.

## 5. 실패·검수 정책

- 파일 처리 성공과 게임에 채택할 승인은 다르다. 미검수 결과는 후보로 보존하되 승인된 동작을 자동 대체하지 않는다.
- 빈 알파, 잘림, 누락된 필수 파일, 빈 타임라인, 지원되지 않는 timing, 저장 미완료/충돌은 출력 차단 사유다.
- 발 추정이 불확실하면 수동 지정 또는 공중 root anchor를 선택한다. bbox를 해부학적 체고로 자동 승인하지 않는다.
- 부분 생성 실패는 성공한 다른 동작을 지우지 않는다. 재생성은 새 버전이며 기존 보정을 무조건 물려주지 않는다.
- provider 인증 준비, 실제 호출 성공, 잔여 사용량을 별개로 표시한다. 잔여량을 모르면 `확인 불가`다. 실제 연동 차단 시 UI와 보고서에 미검증 범위를 남긴다.
- 저장 실패 후 출력으로 진행하지 않는다. 새 편집이 생기면 과거 출력의 기준 revision을 명확히 보여 준다.

## 6. 제외 및 후속 범위

PXF/effect_editer, 노드 이펙트 제작기, 배경 생성, 전투 엔진, 멀티플레이는 제외한다. 다방향 자동 제작, 영상·보간·rig·호흡 고급 효과, 원격 계정/협업, 모바일 편집, 클라우드 공개는 후속이다. 첫 버전은 사이드뷰 중심이며 사용자가 방향을 지정한다.

Next.js 대신 React+Vite를 채택한 이유와 engine pin은 [기술 설계](ARCHITECTURE.md)에 있다. React를 쓴다는 이유로 Python 엔진을 다시 작성하지 않는다. 포크는 프로젝트 내부 소스 사본으로 먼저 구성하며 원격 게시가 현재 구현 완료의 조건은 아니다.

## 7. 출시 판단과 보고

[구현 계획](IMPLEMENTATION_PLAN.md)의 각 단계는 실행 가능한 결과를 남긴다. 중간 milestone을 전체 완성으로 보고하지 않는다. 최종 보고에는 실행 URL/실행법, 실제 출력 파일, 요구별 테스트, 실제 provider 실행 여부, 남은 결함을 포함한다. 연구에서 수행한 19개 관찰 검사는 제품 수용 테스트 결과에 합산하지 않는다.
