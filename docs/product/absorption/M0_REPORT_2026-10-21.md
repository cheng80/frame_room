## 6. Recipe 재현 규칙

`classify_recipe`·`classify_derived`가 동작마다 아래 class를 매긴다. M0 도구(`baseline`, `replay`)는 이 class대로만 동작하고 다른 정책을 조용히 재실행하지 않는다.

**적용 범위:** 아래 class와 "조회 전용", "재개하지 않음"은 M0 진단 결과이자 M1/M2에서 구현할 제안 정책이다. 현재 제품 런타임은 이를 강제하지 않는다. `services/api/main.py`의 `POST /v1/jobs/{jid}/retry`와 `services/worker/video_task.py`는 저장된 `processing.version`을 검사하지 않고 현재 코드(`VERSION = video-processing-v4-sprite-gen-2.34`)로 다시 처리한다. 지금 엔진은 v4 하나뿐이라 실제로 다른 정책이 섞이지는 않는다. 그러나 엔진 helper를 바꾸는 M2 전에 이 차단을 제품 코드에 넣어야 한다. M0에서는 제품 코드를 바꾸지 않았다.

| class | 조건 | 처리 |
| --- | --- | --- |
| `reproducible-current` | `processing.version == video-processing-v4-sprite-gen-2.34`, 옵션 키가 모두 현행 키, 엔진 `qualityVersion == 2.34.0`, 원본 MP4 해시 일치 | `replay`로 다시 확인. 옵션이 없던 시기의 `frameSelection=uniform`, `frameJudge=rules`는 현행 기본값으로만 보충 |
| `legacy-unreproducible` | version이 다름(구버전 또는 미래 v5), 모르는 옵션, qualityVersion이 다름 | M0 replay 제외. 제안 정책: 결과 조회만 허용하고 현재 정책으로 재개하지 않음 |
| `source-missing` | 원본 MP4나 원본 프로젝트가 없음 | M0 replay 제외. 제안 정책: 조회만 허용 |
| `no-recorded-recipe` | 처리 기록이 없음(atlas 복구, raw-v1) | M0 replay 제외. 제안 정책: 조회만 허용 |
| `derived-no-replay` | 원본이 있는 파생 결과 | M0 replay 제외. 저장된 셀이 기준 |

**실제 replay(외부 호출 없음):** 대상은 `reproducible-current` 2건이다(`ffc72403` generate_video, `c67bf6d1` process_video). 저장된 옵션과 spill 참조로 `process_clip`을 다시 실행했다. 이어서 worker와 같은 정규화·GIF 마무리를 거쳤다. 두 건 모두 다섯 가지 확인이 일치했다: 선택 구간 33–59, 샘플 8장과 시간(125·125·125·167·125·125·125·166ms), keyed 픽셀 해시, 최종 셀 해시, loop. `engineMatchesBaseline=true`다. replay 결과물은 검증용 임시 파일이다. 프로젝트나 라이브러리에 등록하지 않았고, 사용자에게 전달하는 동작으로 보고하지 않는다.

**같은 VERSION 문자열의 위험:** extraction cache key(`extractions/<id>/complete.json`)는 `VERSION + MP4 sha + key + reference`만으로 만든다. 저장 기록도 `processing.version`과 `options`만 남긴다. M2에서 엔진 helper(`video/loop`, `frames`, `align` 등)를 교체하면서 VERSION을 그대로 두면 문제가 생긴다. `/jobs/{jid}/retry`가 구 엔진의 keyed cache를 재사용해 새 선택 코드와 섞게 된다. 기록상으로도 같은 recipe로 보여 재현 가능으로 잘못 분류된다. 그래서 M1/M2에서 제품 코드에 구현할 규칙을 다음과 같이 제안한다. 아래 세 규칙은 아직 제품에 없다.

1. 새 정책은 새 VERSION 문자열을 쓴다(예: `video-processing-v5-…`).
2. extraction options와 처리 기록에 엔진 앱 의존 파일 digest와 adapter 버전을 넣는다.
3. 구 VERSION 작업의 checkpoint를 새 정책으로 이어 실행하지 않는다(`/jobs/{jid}/retry`에서 차단).

M0에서 실제로 적용한 것은 도구 범위뿐이다. baseline에 엔진 트리 digest를 고정했고, 엔진이 바뀌면 `replay`가 `engineMatchesBaseline=false`를 보고하고 재현으로 판정하지 않는다. 그 결과는 정책 비교로만 쓴다. 구 recipe 재실행 지원은 이번 범위가 아니다.

### 데이터 접근 기록

첫 replay 시도에서 앱 `video_normalization`의 기본 메타데이터 저장 함수가 `store.managed_path`를 거쳤다. 이 함수가 `.data/app.sqlite3`에 WAL 연결을 열어 `project_folders`를 SELECT한 뒤 경로 이탈 오류로 중단했다. 쓰기는 없었다. `app.sqlite3`의 수정 시각은 2026-10-13 05:16 그대로이고 크기도 같다. `.data` 디렉터리 시각만 바뀌었는데, WAL 임시 파일이 생겼다 지워진 것으로 본다. 이후 replay는 `SPRITE_DATA_DIR`을 work 아래로 격리하고 메타데이터를 직접 저장한다. 그 뒤 baseline verify는 변경 없음이었다. 이 격리 값은 처음 구현에서 `os.environ`에 남았다. 수정 후에는 replay가 끝나면 원래 값으로 되돌린다(10장).

## 8. source와 검증의 한계

- upstream은 소스와 문서를 정적으로 읽었다. upstream 시험, RIFE 성능, 생성 품질은 실행하지 않았다.
- 앱 경로 대응은 코드 대조로 확인했다. 앱 실행이나 브라우저 시험은 하지 않았으므로 앱에서 동작한다는 근거로 쓰지 않는다.
- provider 인증과 ffmpeg 인코더(`libopus`·`aac`) 사용 가능 여부는 확인하지 않았다(인증 접근 금지).
- replay는 현재 정책이 같은 결과를 다시 만든다는 사실만 증명한다. v2.45.3 결과는 아직 하나도 없다.
- 공개 기능 수는 고정 commit의 source 집합과 대장 연결 규칙으로 정했다. 변경 기록이나 웹 문서만 다루는 기능 차이는 대장 밖일 수 있다.
