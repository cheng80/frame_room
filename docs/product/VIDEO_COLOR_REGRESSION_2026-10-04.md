# 영상 후보의 칼·손 색 번짐 회귀 수정

> 2026-10-06 자료 정리: 아래 조사·실험의 원본, 비교 결과와 전용 스크립트는 사용자 요청으로 삭제했다. 제품 결정·구현 기록은 보존하며 과거 경로를 현재 실행 가능한 자료로 해석하지 않는다.

**후속 완료:** GIF의 마지막 색상·알파 정리를 PNG 후보에도 연결했고 실제 프로젝트 v26에 적용했다. 실제 GIF·브라우저 28프레임과 출력 파일 검증은 [웹 품질 보완 완료 기록](WEB_QUALITY_COMPLETION_2026-10-04.md)을 따른다. 아래 v24 결과는 최종 단계 적용 전의 원인 조사 이력이다.

기존 실제 Grok 보행 영상의 후처리를 에디터에 연결할 때 기준 이미지와 축소 방식이 달라졌다. 이번 수정은 같은 MP4를 재사용하며 추가 생성은 0회다.

> 추가 확인: 아래의 “이전 결과와 픽셀 일치”는 **GIF 저장 전 PNG**와의 비교다. 사용자가 좋다고 본 `walk-preview-3x.gif`와 같다는 의미가 아니며, 손·칼 색 깜빡임이 해결됐다는 앞선 결론은 정정한다.

## 사용자가 지정한 GIF와의 차이

`export_preview.py`는 PNG를 3배 nearest 확대한 뒤 `_prepare_transparent_frame(..., 128)`을 적용했다. 이 함수는 RGB를 검정 배경에 알파 합성하고 프레임별 최대 255색으로 양자화하며, 알파 128 이하는 제거하고 나머지는 불투명하게 만든다. 편집기 PNG에는 이 마지막 단계가 없다. 원래 남아 있던 일부 노랑·초록이 GIF 팔레트에서 갈색·회색으로 바뀌어 덜 두드러졌다.

- 동일한 61번 원본 프레임의 손 픽셀 `(44, 73)`은 PNG에서 `(160,139,35,252)`, GIF에서 `(153,106,69,255)`다. 위치는 편집기 발 앵커 이동 전 좌표다.
- 이전 PNG에 GIF의 마지막 저장 단계를 그대로 재적용한 결과, 사용자가 지정한 **실제 3배 GIF의 28프레임 모두 픽셀 차이 0개**다. 단순히 GIF 특성을 추측한 것이 아니라 파일 전체를 재현했다.
- 저장된 수정 에디터 PNG는 발 앵커 위치를 맞추면 이전 PNG와 28프레임 모두 일치한다. GIF와 PNG 사이에는 프레임당 2,446–3,083개 픽셀이 다르다. 이 수에는 색상과 알파 변경이 모두 포함되며, 모두 오류 픽셀이라는 의미는 아니다.
- 이번 비교는 원본 파일 분석이며 에디터나 기존 프로젝트를 변경하지 않았다. 추가 AI 생성 0회. GIF 팔레트는 프레임별이므로 일반적인 시간축 색상 안정화 기능으로 간주하지 않는다.

재현 스크립트·측정 JSON·같은 프레임 비교 이미지는 `.data/experiments/gif-vs-editor-20261005/`에 보존했다. 에디터에 GIF와 같은 결과를 적용하려면 원본 RGBA를 보존하면서 이 출력 보정 단계를 별도로 적용해야 한다.

## 원인

1. 이전 실험은 `input-canvas.png`를 참조한 `spill=auto` 판정으로 `full` 보정을 적용했다. 에디터 실험은 MP4를 가져온 영상으로 등록하면서 기준 연결을 생략해 `small` 보정만 적용됐다. 예를 들어 원본 61번 프레임에서 735개 픽셀이 이전 keyed 결과와 달랐고, 불투명 마젠타 잔류 픽셀은 187개였다. 이전 결과는 같은 기준에서 0개였다.
2. 이전 PNG는 `video.loop.build_strip`의 공통 영역·Lanczos 축소를 거쳤지만 에디터는 디코딩 크기의 프레임을 nearest로 바로 축소했다. 미세한 녹색·노란색 점이 더 두드러지고 윤곽도 달라졌다. 이 색이 모두 새로 생성된 것은 아니며, 원본 영상에도 일부 존재한다.

## 수정

- 기존 영상 처리에 `색 번짐 판정 기준`을 추가했다. 같은 프로젝트의 원본 그림을 명시해 판정한다. 실제 키 색 의상이 있는 기준은 계속 보수적으로 처리한다. 연결된 기준이 없으면 약한 보정임을 안내하며 아무 그림도 임의로 고르지 않는다.
- 생성한 영상은 기존처럼 저장된 생성 기준을 사용한다. 투명 PNG도 영상 키 색으로 합성해 판정한다. 키 색은 자동 설정일 때 영상 첫 프레임에서 감지한다.
- 원본 프레임·원래 크기의 keyed PNG·편집 크기 PNG를 각각 보존한다. 전체 선택 구간의 공통 영역과 첫 프레임 체고로 Lanczos 축소를 한 번 적용한 뒤, 기존 편집기는 배율 1부터 nearest를 사용한다. 후보 수를 줄여도 공통 영역은 유지하며 포즈마다 fit하지 않는다.
- 발 기준점은 공통 영역의 하단으로 교체하지 않고, 원래 첫 프레임 앵커를 새 이미지 좌표로 변환한다. 구간이나 무기 돌출 범위가 달라도 동일한 원본 발 기준을 유지한다.
- 기준 자산 ID·판정·정규화 좌표를 출처에 기록한다. 기준은 동시 이력 복원과 ZIP 백업/복원에서도 보존된다.

## 실제 프로젝트 복구와 검증

프로젝트 `9717eb79-f63f-40ab-adda-149697e2c8db`의 기존 28프레임·14프레임 동작을 보정 후보로 다시 연결했다. 기존 이미지와 이력은 남겨두었으며, 슬롯 ID·이름·표시 시간·변형·픽셀 편집값을 유지했다. 앵커 보완까지 적용한 복구 시점은 v24다.

- RGB 준비 캔버스와 원본 RGBA 기준 모두 기존 keyed **73프레임 전체와 픽셀 일치**.
- 축소 이미지 내용은 **28프레임 모두 이전 PNG와 픽셀 차이 0개**. 최종 편집기 배치는 원래 발 앵커를 유지하므로 과거 미리보기보다 오른쪽 1px·아래 2px다. 이 위치 차이를 맞춘 최종 렌더도 픽셀 차이 0개다. 알파 0의 숨은 RGB는 동일한 0으로 정규화해 비교했다.
- 28프레임·14프레임 모두 총 **1,167ms** 유지.
- 실제 bake의 PNG·아틀라스 RGBA 일치, 잘림 등 기하 오류 없음. 수동 승인은 계속 대기 상태.
- Python 통합 **313개**, 프런트엔드 **161개** 통과, TypeScript·Vite 빌드 성공.
- 이번 수정 이후 브라우저 조작 검사는 하지 않았다. 후보 생성·프로젝트 수정·저장과 bake는 실행 중인 앱 API와 worker로 검증했다.
