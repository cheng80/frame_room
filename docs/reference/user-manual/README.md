# HTML 사용 설명서 제작 기준

2026-10-06 KST · 프레임룸의 구성과 스타일 + 기존 대화의 사용자 제약

다른 프로젝트의 설명서를 만들 때 사용하는 공통 참고 문서다. **프레임룸의 설명서 구성을 기준으로 삼고, 이펙트 에디터에서 추가로 지시한 글자 가독성·이미지 확대·패닝·선명도 조건을 함께 적용한다.** 현재 프레임룸에 이 조건이 모두 구현되어 있다는 뜻은 아니다.

이 문서의 **사용자 지시**는 대화에서 확인한 요구다. **구현 참고**는 소스에서 확인한 방식이다. **권장 기본값**은 다음 작업을 위한 제안이며, 사용자가 특정 수치를 직접 정했다는 뜻이 아니다. 새 프로젝트의 명시적 요청과 현재 작업 규칙을 먼저 적용한다.

## 1. 반드시 이어받을 사용자 요구

1. 실제 판매 제품의 설명서 수준으로 만든다. 글만 나열하지 않고 실제 제품 화면과 따라 하는 절차를 함께 제공한다. [U01]
2. 처음 결과를 만드는 **퀵스타트**와 필요한 기능을 찾아보는 **상세 설명서**를 구분한다. 프레임룸은 HTML 설명서의 참고 사례다. [U02–U03]
3. 기존 설명서를 개선할 때는 목차·섹션·배치의 구조를 유지한다. 글자가 커져 필요한 줄바꿈·여백 조정은 하되, 가독성 개선을 이유로 임의로 전면 재설계하지 않는다. [U04]
4. **설명서 본문 자체가 읽기 쉬워야 한다.** 이미지 확대 기능이 있어도 작은 본문·메뉴·캡션 문제가 해결된 것은 아니다. [U05]
5. 작은 확대 버튼뿐 아니라 **이미지 자체를 클릭해 큰 팝업을 연다.** 팝업 안에서 확대·축소하고, 확대된 이미지를 마우스로 잡아 이동할 수 있어야 한다. [U06–U08]
6. 확대했을 때 노드명·버튼명·수치가 읽히는 선명한 원본을 쓴다. 흐린 이미지를 크게 표시하는 것만으로 완료 처리하지 않는다. [U09]
7. 제품 화면과 사용 흐름이 바뀌면 설명서의 이미지·메뉴 위치·절차도 갱신한다. 실행 환경 안내만 고치는 것으로 끝내지 않는다. [U10]

대화 원문과 각 요구의 범위는 [출처 문서](USER_REQUESTS.md)에 있다. 이하 수치와 구현 방식은 이 요구를 충족하기 위한 기준안이다.

## 2. 프레임룸에서 가져올 구성과 스타일

### 읽는 흐름

| 영역 | 구성 원칙 |
| --- | --- |
| 상단 | 제품명, 퀵스타트/상세 설명서 전환, 앱 열기, 필요한 다운로드·인쇄 |
| 첫 화면 | 무엇을 만들 수 있는지, 준비물, 첫 결과 예시, 시작 위치 |
| 퀵스타트 | 준비 → 입력 → 핵심 작업 → 결과 확인 → 저장/내보내기의 짧은 경로 |
| 상세 설명서 | 실제 작업 순서에 맞춘 장 구성, 기능 찾기, 대안 경로, 실패·복구 안내 |
| 각 단계 | 번호와 목표 → 실제 화면 → 누를 곳과 입력값 → 정상 결과 → 막힐 때 확인 |
| 탐색 | 넓은 화면의 고정 목차, 좁은 화면의 접이식 목차, 현재 위치, 상세 문서 검색 |
| 보충 | 단축키의 작동 조건, FAQ, 상태 용어, 저장 위치와 복구 방법 |

프레임룸은 퀵스타트 6단계, 상세 본문 11개 장과 단축키·문제 해결을 합친 13개 섹션, FAQ 22개로 구성되어 있다. **이 개수는 다른 프로젝트에 강제하지 않는다.** 프로젝트의 첫 성공 경로에 맞춰 줄이거나 늘린다.

한 단계는 “버튼을 누르세요”에서 끝내지 않는다. 예를 들어 “후보를 고른 뒤 순서에 추가 → 타임라인에 슬롯이 생김 → 보이지 않으면 선택 상태 확인”처럼 행동과 확인 결과를 연결한다. 자동 검사, 사람의 승인, 저장 완료, 내보내기 완료처럼 의미가 다른 상태를 섞지 않는다.

### 시각적 기준

프레임룸은 따뜻한 밝은 배경, 짙은 녹색 첫 화면, 녹색 강조, 얇은 구분선과 여백을 사용한다. 화면 이미지는 어두운 상단 막대가 있는 프레임 안에 두고 설명을 바로 아래에 붙인다. 과도한 장식보다 제목·단계·화면의 위계로 안내한다.

| 역할 | 프레임룸 값 | 재사용 방법 |
| --- | --- | --- |
| 전체 배경 | `#f4f4ee` | 긴 문서를 읽는 밝고 차분한 면 |
| 본문 | `#1c302c` | 충분히 진한 기본 글자 |
| 보조 글자 | `#566963` | 크기까지 작게 낮추지 않기 |
| 구분선 | `#d7ded6` | 장·표·이미지 경계를 정리 |
| 강조 / 연한 강조 | `#165d47` / `#c4f0d1` | 현재 위치, 주요 행동, 번호 |
| 카드 / 어두운 면 | `#ffffff` / `#152c26` | 설명 영역과 첫 화면·확대 뷰 구분 |

브랜드에 맞게 색은 바꿔도 된다. 원형 번호, 절제한 모서리, 단계별 여백, 이미지 아래 캡션이라는 표현 방식을 우선 가져온다. 한 페이지의 모든 요소를 큰 카드로 감싸거나 대시보드처럼 만들 필요는 없다.

구현 참고: 본문 바깥 최대 폭 `1260px`, 데스크톱 목차 `210px`, 목차와 본문 간격 `50px`, 좌우 여백 `30px`; 중간 폭에서는 목차 `175px`·간격 `28px`, 작은 화면에서는 단일 열·좌우 여백 약 `18–20px`다. 현재 분기점은 `1000px`와 `760px`다. 새 글자 크기와 긴 제목을 기준으로 다시 조정한다.

## 3. 글자 크기와 가독성

**공간이 부족하면 줄바꿈·열 수·여백·목차 배치를 조정한다. 글자를 10–12px로 줄여 화면에 억지로 넣지 않는다.** 이미지 속 UI 글자와 HTML 본문의 글자를 따로 확인한다.

아래는 권장 기본값이다. 당시 사용자의 요구는 “글자가 너무 작다”였으며 정확한 px 수치를 지정하지는 않았다. 이펙트 에디터에서는 그 요구를 본문 데스크톱 `17px`, 모바일 `16px`, 캡션 `14px`로 구현했다.

| 요소 | 넓은 화면 | 좁은 화면 | 적용 기준 |
| --- | --- | --- | --- |
| 본문·단계 설명·FAQ 답변 | `17–18px` | `16–17px` | 본문은 `16px` 상당 아래로 줄이지 않는 것을 기본 수용 기준으로 삼기 |
| 표의 주요 내용·설정 설명 | `16px` 이상 | `16px` 이상 | 열을 줄이거나 표 안에서만 가로 스크롤 |
| 목차·메뉴·버튼 | `15–16px` | `15–16px` | 중요 작업 버튼은 `16px` 우선 |
| 캡션·보조 안내 | `14px` 이상 | `14px` 이상 | 중요한 조건·주의사항은 본문 크기로 올리기 |
| 문서 제목 | `34–54px` | `30–36px` | 긴 한글 제목은 여러 줄 허용 |
| 장 제목 | `26–30px` | `23–26px` | 본문과 구분되는 크기·여백 |
| 소제목 | `18–22px` | `18–20px` | 지나친 자간 축소 피하기 |

본문 줄간격은 `1.7–1.8`, 제목은 `1.3–1.4`를 출발점으로 삼는다. 한 줄이 지나치게 길어지지 않도록 본문 폭을 조정하고, 연한 회색의 작은 글자로 필수 정보를 표현하지 않는다. 한글 시스템 폰트 대체 경로를 마련해 외부 폰트 없이도 읽을 수 있게 한다.

가급적 `rem`과 단위 없는 줄간격을 사용한다. 브라우저 기본 글꼴 크기와 확대 설정을 막지 않는다. `16px` 기본 환경에서 `1.0625rem`은 `17px`, `0.875rem`은 `14px`에 해당한다. 기존 앱에 설명서를 넣을 때는 설명서 범위의 스타일로 한정한다.

검수 시 `320px`·`390px` 폭, 일반 데스크톱 폭, 브라우저 `200%` 확대를 확인한다. 글자 확대 때문에 문장이 잘리거나 닫기 버튼이 사라지면 레이아웃을 고친다. 버튼은 충분한 클릭 면적을 확보한다. `44×44 CSS px` 상당을 권장 출발점으로 삼되 이 수치도 당시 사용자 발언은 아니다.

인쇄는 별도로 점검한다. 본문 `11–12pt`, 캡션 `10pt` 이상을 출발점으로 삼고, 한 장에 맞추려고 전체를 과도하게 축소하지 않는다. 화면용 px와 인쇄용 pt를 같은 수치로 비교하지 않는다.

## 4. 실제 화면과 이미지 원본

- 현재 제품의 실제 버튼명·패널 배치·작업 상태가 보이는 화면을 쓴다. 변경 전 화면은 “이전 버전”으로 표시하거나 교체한다.
- 전체 화면은 위치를 찾는 데, 부분 확대 이미지는 작은 설정·노드·수치를 읽는 데 쓴다. 둘을 연결하는 번호와 캡션을 둔다.
- UI 스크린샷에는 일반적인 이미지 보간을 사용한다. `image-rendering: pixelated`는 픽셀 아트 결과물에만 적용하고 설명서의 모든 이미지에 전역 적용하지 않는다.
- 확대용 원본은 실제 캡처 해상도를 유지한다. 작은 썸네일을 팝업에서도 재사용하거나, HTML `width`만 크게 적어 고해상도라고 표시하지 않는다.
- 권장 출발점은 최종 표시 폭과 화면 배율을 고려한 캡처다. 예를 들어 `1200 CSS px` 폭을 DPR 2에서 선명하게 보이게 하려면 약 `2400px` 폭의 원본이 필요하다. 노드가 빽빽한 화면은 별도 부분 캡처도 제공한다. DPR 수치만으로 가독성 검증을 대체하지 않는다.
- 텍스트·선이 많은 화면은 PNG나 선명도가 유지되는 형식을 우선 검토한다. JPEG를 쓰면 압축 흔적을 확대해 확인한다.
- 계정·인증값·개인 경로 등 공개하지 않을 정보는 캡처 전에 정리한다. 설명에 필요한 실제 동작이나 결과를 다른 것으로 바꿔 그리지 않는다.
- 파일별로 캡처 날짜, 제품 버전 또는 커밋, 화면 크기·배율, 출처, 필요한 처리 내역을 기록한다. 실제 캡처, 화면 스타일 PDF 렌더, AI 생성 원본, 가져온 파일, 추출·배경 제거 결과, 합성 시험 이미지를 구분한다.

프레임룸의 화면 파일은 현재 12장이고 해상도는 `1440×960`, `1600×1050`, `3360×1974` 등으로 다르다. 모든 이미지의 크기를 `1600×1050`이라고 가정하지 않는다. 이펙트 에디터의 개선 사례는 실제 화면을 `5760×3600` 또는 `5760×4480`으로 다시 캡처한 것이며, **5760px을 모든 프로젝트의 의무 해상도로 삼는 것은 아니다.**

## 5. 이미지 확대 팝업의 완료 조건

사용자 요구를 만족하는 확대 기능은 다음 동작을 포함한다.

1. 이미지 자체와 별도 “크게 보기” 버튼으로 같은 팝업을 연다. 키보드로도 진입할 수 있게 한다.
2. 처음에는 전체 이미지가 보이는 화면 맞춤으로 연다. 제목·캡션을 유지한다.
3. 확대·축소 버튼, 배율 표시, 화면 맞춤 복귀, 원본 보기, 닫기를 제공한다. “화면 맞춤/원본 크기” 두 상태 전환만으로 확대 요구가 끝났다고 보지 않는다.
4. 확대된 이미지를 마우스 기본 버튼으로 잡아 가로·세로로 이동한다. 버튼 조작과 이미지 드래그를 구분하고, 드래그가 끝나면 이동 상태가 풀린다.
5. 이미지 가장자리까지 볼 수 있고, 이미지가 화면 밖으로 사라져 돌아올 수 없는 상태를 만들지 않는다. 스크롤과 키보드 접근도 유지한다.
6. 화면이 좁아지면 툴바를 여러 줄로 배치한다. 확대 상태에서도 닫기·화면 맞춤을 사용할 수 있게 한다.
7. Escape와 닫기 버튼으로 닫고, 열었던 이미지 버튼 또는 확대 버튼으로 초점을 돌려준다. 배경 클릭 닫기를 제공하면 실제 동작을 확인한다.
8. 같은 팝업을 다시 열 때 확대·스크롤·패닝 상태를 일관되게 초기화한다. 이미지 위 안내 번호를 누르면 안내만 바뀌고 팝업이 덩달아 열리지 않게 한다.

구현 참고: 이펙트 에디터는 기본 `<dialog>`, 명시적 배율 상태, 포인터 캡처와 스크롤 위치를 이용한다. 별도 이미지 뷰어 라이브러리가 필수는 아니다. 당시 구현의 범위는 `5–300%`, 버튼 변화량은 `25%p`다. 이 수치는 예시이며 원본 해상도와 용도에 맞게 조정한다. 첫 확대를 누를 때 현재 화면 맞춤보다 작아지는 오류를 피한다.

이 문서에서 원본 `100%`는 이미지 원본 픽셀 폭을 같은 수의 CSS px로 표시한다는 뜻이다. 고밀도 디스플레이의 물리 픽셀과 1:1이라는 뜻은 아니다. UI에 표시하는 배율의 기준을 일관되게 정한다. 휠 확대·핀치 확대는 추가 선택 기능이며 사용자 원문의 필수 조건과 구분한다.

## 6. 필요한 체험만 추가

프레임룸의 참고 기능은 클릭형 화면 번호 안내, 단계 완료 체크, 로컬 검색, 예제 재생, 시간 조절, 요청 예시와 복사다. 모두 설명을 이해하는 데 도움이 되는 경우에만 가져온다.

- 실제 결과물을 사용하고 출처를 표시한다. 단순 도형이나 합성 자료를 실제 AI 생성 결과처럼 소개하지 않는다.
- 체험을 실행해도 사용자 프로젝트가 바뀌거나 유료 생성 요청이 발생하지 않게 한다. 실제 앱 실행으로 이어지는 버튼은 그 목적을 명시한다.
- 애니메이션은 정지 상태에서 시작하고 재생·정지·첫 화면 복귀를 제공한다. 탭이 숨겨질 때와 인쇄할 때 정지하도록 한다. 움직임 줄이기 설정도 고려한다.
- 단계 완료 체크는 사용자의 읽기·따라 하기 확인이다. 제품의 자동 검증이나 작업 승인과 혼동시키지 않는다. 저장되지 않는 체크 상태라면 이를 안내한다.
- 복사는 사용자가 누를 때만 실행한다. 권한이 없으면 문구 선택과 수동 복사 안내를 제공한다.
- 오래된 예제를 유지한다면 현재 기본값과 다름을 설명한다. 프레임룸의 6장 시간 체험과 현재 걷기 기본 8장은 같은 기준이 아니다.

## 7. 오프라인·인쇄·유지보수

HTML 기본 본문, 목차, 이미지는 JavaScript가 꺼져도 읽을 수 있게 만든다. 스크립트가 필요한 버튼은 준비되지 않은 상태에서 작동하는 것처럼 보이지 않게 한다.

오프라인 배포가 필요한 경우 HTML/CSS/JS/이미지를 상대 경로로 묶고 `file://`로 확인한다. 기본 읽기에 CDN·로그인·서버·원격 폰트를 요구하지 않는다. 정적 HTML에 데이터를 넣거나 호환되는 로딩 방식을 사용해 로컬 파일에서 `fetch` 제한으로 본문이 비지 않게 한다. 앱 열기에는 실행 중인 앱이, 외부 영상에는 인터넷이 필요하다는 경계를 안내한다.

퀵스타트와 전체 가이드 영상은 보조 자료로 연결할 수 있다. 영상 없이도 핵심 절차를 따라갈 수 있어야 한다. 프레임룸의 [퀵스타트 영상](https://youtu.be/yZgaGipvkkg)과 [전체 가이드 영상](https://youtu.be/MCCSBxyghXQ)은 README에 연결한 사례이며 모든 설명서에 영상을 새로 만들라는 요구는 아니다.

인쇄에서는 고정 목차·검색·조작 버튼을 정리하고, FAQ 내용을 펼치고, 애니메이션을 정지 이미지로 바꾼다. 제목과 이어지는 내용, 이미지와 캡션이 불필요하게 갈라지지 않는지 확인한다. PDF는 확대 팝업을 대신할 수 없으므로 필요한 세부 이미지를 지면에도 제공한다.

생성형 설명서는 **원본 콘텐츠·스타일·동작·생성기**를 수정한 뒤 HTML을 다시 만든다. 생성된 HTML만 고쳐 다음 빌드에서 사라지는 변경을 만들지 않는다. 다음과 같이 역할을 나누면 다른 프로젝트에서도 관리하기 쉽다.

```text
public/guide/
  index.html              # 읽는 사람용 퀵스타트
  manual.html             # 읽는 사람용 상세 설명서
  guide.css / guide.js    # 공통 스타일과 필요한 상호작용
  screens/ / media/       # 제품 화면과 실제 예제
  content.json            # 사용하는 경우 콘텐츠 원본
scripts/
  generate-guide.*        # 생성 방식인 경우
  package-guide.*         # 오프라인 배포가 필요한 경우
docs/
  USER_GUIDE_VERIFICATION.md
```

프레임룸의 `npm --prefix apps/web run guide:build`는 HTML을 생성하고, `engine/sprite-gen/.venv/bin/python scripts/package-guide.py`는 읽는 사람용 ZIP을 만든다. 다른 프로젝트에서는 그 프로젝트의 명령으로 바꾼다. 배포 ZIP과 수정 가능한 제작 소스는 구분하며, 프로젝트 데이터·인증 파일·불필요한 작업 기록을 통째로 넣지 않는다.

## 8. 현재 프레임룸과 목표의 차이

2026-10-06 소스 확인 기준이다. 다음 작업자가 구현 여부를 잘못 물려받지 않도록 남긴다.

| 항목 | 프레임룸 현재 구현 | 재사용 시 적용할 기준 |
| --- | --- | --- |
| 퀵스타트/상세, 목차, 검색, FAQ | 구현됨 | 구조를 가져오되 새 제품의 실제 흐름으로 작성 |
| 본문과 보조 글자 | 본문 `15px`, 목차 `12px`, 캡션 `11px`; 모바일 일부 `8–11px` | 3절의 가독성 기준으로 보완. 기존 수치를 그대로 복사하지 않음 |
| 이미지 팝업 진입 | `[data-screen]` 확대 버튼 | 이미지 자체 클릭도 지원 |
| 팝업 확대 | 화면 맞춤/원본 크기 전환, 스크롤 | 명시적 확대·축소·배율·맞춤 복귀 |
| 마우스 패닝 | 전용 구현 없음 | 확대 상태에서 잡아 이동 |
| 키보드 닫기·초점 복귀 | Escape/닫기와 호출 버튼 복귀 코드 있음 | 실제 브라우저에서 다시 확인 |
| 이미지 선명도 | 여러 해상도와 캡처/PDF 렌더 출처가 섞임 | 화면별 원본·출처와 확대 가독성 점검 |
| 체험 재생 | 기본 정지, 탭 숨김 정지 | 새 체험도 동일 원칙 적용 |
| 인쇄 시 정지 | 전후 WebP는 처리됨; canvas 플레이어의 일괄 정지 처리는 없음 | 모든 움직임과 정지 대체 화면을 확인 |
| 오프라인 배포 | 정적 HTML과 상대 자산 ZIP | 새 배포본을 별도 검사 |

이펙트 에디터에는 이미지 클릭, 확대·축소, 마우스 패닝, 본문 17/16px와 고해상도 화면 개선이 별도로 구현되어 있다. **이펙트 에디터의 완료 이력을 프레임룸의 완료 이력으로 합치지 않는다.**

## 9. 검증과 작업 방식

현재 프로젝트의 브라우저 검증 규칙은 **ego-browser 사용, 기존 TaskSpace 재사용, 사용자 마우스와 작업 창을 가로채지 않기, Chrome·별도 Chromium 설치/실행 금지**다. 다른 프로젝트에서도 먼저 현재 규칙과 이용 가능한 도구를 확인한다. 도구 사용이 막히면 성공한 정적 검사와 실행하지 못한 브라우저 검사를 분리해서 기록한다.

링크·파일·빌드 검사만 통과했다고 읽기 편함이나 확대·패닝까지 검증한 것으로 표시하지 않는다. [검수표](CHECKLIST.md)에 버전, 날짜, 환경, 실제 동작 결과를 남긴다. 과거의 커밋·push·배포 허가는 새 설명서 작업의 허가로 재사용하지 않는다.

프레임룸의 2026-10-06 설명서 기록에는 빌드·링크·미디어·ZIP 검사가 있지만, 당시 ego TaskSpace 연결 실패로 그 갱신의 화면·클릭·반응형 검사는 미실행이다. 2026-10-03의 브라우저 검증과 구별한다. 이펙트 에디터의 확대·패닝 검증은 2026-10-05의 별도 이력이다.

이 참고 문서 작성에서는 과거 사용자 메시지, 현재 CSS/JS/컴포넌트, 이미지 파일 크기와 기존 검증 기록을 대조했다. **앱이나 설명서를 수정하거나 브라우저로 재검증한 작업은 아니다.**
