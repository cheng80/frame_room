# 우선순위 구현 계획과 수용 테스트

작성일: 2026-10-03. **조사·설계 문서이며, 앱 구현 또는 실제 생성 provider 연동의 완료 보고가 아니다.** 기존 [구현 명세](../IMPLEMENTATION_SPEC.md)의 A1–A14를 재현 가능한 수용 기준으로 세분화했다. 기존 문서는 수정하지 않았다.

이 문서의 수치 허용오차, 단계별 완료 기준, 실패 정책은 새 앱을 위한 **설계 제안**이다. 공개 제작 노트가 이 테스트 체계나 앱을 이미 구현했다는 뜻은 아니다. 실제 로컬 엔진 실험 결과는 [validation.md](validation.md)에 따로 기록한다. 엔진 단위 실험이 통과해도 아래 전체 앱 테스트의 `NOT_RUN`을 자동으로 `PASS`로 바꾸지 않는다.

## 1. 먼저 끝낼 경로

첫 구현 목표는 **기존 PNG 가져오기 → 알파·추출 검수 → 공통 배율·발 정렬 → 후보·순서 편집 → 저장·복원 → 동일한 최종 픽셀을 미리보기와 출력에서 사용**하는 경로다. 생성 품질이 나쁘거나 provider가 연결되지 않아도 이 경로를 검증할 수 있어야 한다.

그다음 기준 승인, 생성 설정, 작업 실행·취소·복구를 붙인다. mock으로 작업 UI를 검증하는 단계와 실제 provider 결과를 가져오는 단계는 서로 다른 완료 단계다. **이번 조사에서는 유료 생성 호출을 하지 않는다.** 실제 provider 수용 시험은 후속 구현 시 호출 범위가 허용된 환경에서만 수행하며, 수행하지 못했으면 기능 상태를 `실제 연동 미검증`으로 남긴다.

초기 구현은 React + Vite 화면, Python API와 별도 작업 실행기, 프로젝트 전용 `sprite-gen` 포크를 전제로 한다. 프런트엔드 교체 여부와 관계없이 긴 작업과 원본 파일 관리는 Python 계층이 맡는다. 확정 아키텍처·구체적인 API 이름은 이 폴더의 설계 문서와 함께 적용한다.

[데이터 계약](data-contract.md)의 **균등 FPS+명시적 hold 복제**는 먼저 검증하는 작은 중간 단계다. 이 단계에서 아직 지원하지 않는 가변 duration UI는 비활성화하고 제한을 표시한다. 이 문서의 **P0 최종 완료**에는 TEST-20/21의 occurrence별 가변 duration 저장·미리보기·출력 지원까지 필요하다. 균등 FPS 경로만 통과한 상태를 P0 전체 또는 가변 시간 지원 완료로 보고하지 않는다.

### 수치·좌표·판정의 기준

- bbox는 오른쪽/아래가 제외되는 `[x0,y0,x1,y1)`다. 높이는 `y1-y0`. 셀은 `512×512`, 바닥 여백은 `18`, 목표 바닥선은 `y=494`다. 가장 아래 유효 픽셀 행 `493`과 기준선 `494`를 혼용하지 않는다. 가장자리 `2px`은 거너 프리셋이다.
- 형상 support는 `alpha>0`, 발 후보 추정은 프리셋에서 `alpha>=16`으로 분리한다. 약한 알파가 잘리는지 확인할 때 발 임계값을 재사용하지 않는다.
- 공통 배율 `s`는 캐릭터·방향의 승인된 기준 체고에 대해 한 번 정한다. `471px`와 `320px`는 이 거너 포즈의 전체 알파 bbox 실측치이며, 무기를 제외한 몸 체고의 일반 정의로 대체하지 않는다.
- 동일 배율에서 높이 비율 목표는 `320/471 ≈ 0.679406`이다. `s=1`인 정수 이동에서는 높이 `471/320`이 정확히 유지되어야 한다. 소수 배율에서는 각각 `|측정 높이−원본 높이×s|≤1px`를 허용하며, 둘 중 한 자세에만 독립 배율을 적용하는 것은 허용하지 않는다.
- 저장한 앵커 좌표와 사용자 offset은 동일 좌표계에서 정확히 복원한다. raster 출력에서 접지 오차는 최종 반올림으로 `≤1px`, 공통 scale 또는 몸 표식의 비율 변경은 `0`건이어야 한다. 공중 자세의 의도된 높이를 발 정렬 오류로 계산하지 않는다.
- 출력 픽셀 동등성은 PNG 파일 byte hash가 아니라 **디코딩된 RGBA 배열**로 비교한다. 압축 메타데이터가 달라도 픽셀이 같을 수 있다. 원본 불변 시험은 원본 파일의 SHA-256으로 한다.
- 기존 엔진 연산을 비교하는 연구 oracle는 alpha와 `alpha>0`인 픽셀의 RGBA다. 제품의 TEST-22는 [아키텍처](architecture.md)의 **최종 승인 preview와 PNG/atlas가 동일한 baked bitmap을 사용**하므로 전체 decoded RGBA 차이 `0`을 요구한다. 투명 픽셀의 숨은 RGB 정규화가 필요하면 이 공통 bitmap을 확정하기 전에 한 번 수행한다. 화면 screenshot이나 별도 JS transform 결과를 원본 bitmap 대신 비교하지 않는다.
- 각 실행 보고서에는 test ID, fixture URI/종류/해시, 엔진 commit, 앱 commit, 설정 snapshot, 실행 일시, 판정자, artifact 경로, 실제 값, 기대 값, 상태를 남긴다. 비밀키는 기록하지 않는다.
- 상태는 `NOT_RUN / PASS / FAIL / BLOCKED`로 기록한다. fixture 또는 실제 호출 권한이 없어 실행할 수 없으면 `PASS`가 아니라 `BLOCKED`다. 아래 표의 현재 상태는 전부 `NOT_RUN`이다.

## 5. 실패 시 채택 정책

프레임마다 `처리 성공`과 `게임에 채택 가능`을 구분한다. 파일이 생겨도 얼굴·무기·몸 비율·방향, 알파 잔여, 발 앵커가 검수되지 않았으면 승인 상태가 아니다. 외형 기준이 바뀌거나 generation version이 바뀌면 이전 검수의 적용 범위를 화면에 표시한다.

셀 초과, 빈 알파, 필수 참조 누락, 지원하지 않는 duration 정보가 있는 출력 형식은 해당 출력의 차단 사유다. 발 추정 실패는 자동 배치 확정이 아니라 수동 지정/공중 자세 설정으로 해결한다. 앵커와 무기 제외 몸 체고는 이미지 의미를 해석해야 하므로 모든 입력에서 자동화가 정확하다고 보장하지 않는다.

외부 생성 요청 접수 여부가 불명확하면 작업을 새로 만드는 대신 먼저 이전 job을 조회한다. 네트워크 오류만으로 외부 서비스의 중복 과금이 절대 없다고 보장할 수 없으므로, UI는 미확인을 표시하고 자동 재전송을 중단한다. provider의 idempotency/취소/조회 지원 범위를 실제 어댑터마다 문서화해야 TEST-26–28의 실제 연동 판정을 내릴 수 있다.
